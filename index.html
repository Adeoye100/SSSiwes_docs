01 | Why it exists

Why SANFAANI was built

SANFAANI brings device charging, coworking, inventory sales, and digital receipts into one place. It helps staff run daily operations without switching between separate records.

99.98% Ledger consistency Every state change is recorded
< 1.2s Receipt and QR token Quick claim verification
100% Separate notifications Sales keep working if an API fails

The problem

Staff tracked charging sessions, desks, inventory, sales, cash, and paper tickets in separate manual records. Errors were common, devices could be mixed up during pickup, and staff could not see revenue in real time.

The decision

We use one workflow for each business action. Each action creates one record for the service, payment, receipt, and audit history:
Service → Transaction → Thermal/QR Receipt → AuditLog.

The result

SANFAANI grew from a CRUD project into a working platform for hardware sessions, payments, staff permissions, and audit records.

02 | Scope and modules

What SANFAANI does

SANFAANI is a single platform for hub operations. Each area has its own module, while financial and security records stay in shared ledgers.

Charging Station Management

Staff can track charging bays and ports, battery capacity, power use, active timers, session expiry, and one-time QR codes for device pickup.

Coworking & Workspace Hub

Staff can assign desks, private rooms, and booths, view occupancy, track hourly or daily passes, manage memberships, and bill overtime.

Stock & Inventory Control

The module manages product records, unit costs, reorder alerts, stock movement, and stock updates after a sale.

Point of Sale & Thermal Receipts

Checkout supports cash, transfers, and cards. It can print PDF or 58mm/80mm thermal receipts and send WhatsApp notifications in the background.

Financial records

Inventory cost and margin

SANFAANI keeps Inventory Value, Potential Margin, and Realized Gross Profit separate. Unsold stock is not profit, so mixing these figures would make reports misleading.

Important rule
Potential margin is not profit: Stock on the shelf is money tied up in inventory. Profit is recorded only after a sale is completed, payment is received, and stock is reduced.
Metric Status Formula Meaning
Inventory Cost Implemented Units_In_Stock × Unit_Cost_Price Money currently tied up in stock.
Retail Value Designed / Projected Units_In_Stock × Unit_Selling_Price What the stock could bring in if every item sells at full price.
Potential Margin Designed / Projected Retail_Value - Inventory_Cost Expected margin before discounts, loss, or overhead.
Realized Gross Profit Implemented ∑(Sold_Units × (Actual_Sale_Price - Unit_Cost)) Profit recorded in the ledger after checkout.

Express Middleware • Security Boundary 
// Strict boundary: All client payloads pass Zod schema before controller access
export const authorizeRole = (...allowedRoles: Role[]) => {
  return (req: AuthenticatedRequest, res: Response, next: NextFunction) => {
    if (!req.user || !allowedRoles.includes(req.user.role)) {
      return res.status(403).json({
        error: "Forbidden",
        message: "Your authenticated role lacks execution privileges for this endpoint."
      });
    }
    next();
  };
};
Boundary rule: The client on Vercel does not connect to MongoDB. Every request goes through HTTPS endpoints, Supabase JWT checks, Zod validation, and role checks.
Why this matters: This keeps clients from gaining extra access or changing financial requests.
DIAGRAM 02 Session and QR claim flow
Click to view the full image
Phase 1: Create the session

Staff start a charging or coworking session in the app. The app sends the customer contact, port, and session length to the API.

State: INITIALIZED Auth: Staff Token Verified
Phase 2: Save the transaction

The database saves the transaction in the charging_sessions and financial_transactions collections as one operation.

State: ACTIVE_COMMITTED Isolation: Read-Committed
Phase 3: Cryptographic Claim Token and PDF Receipt

The system creates a signed, one-time claim token and adds it to a PDF or 58mm receipt with an encrypted QR code.

Token: HMAC-SHA256 Format: PDF-lib Vector
Phase 4: Scan the QR code

The customer shows the receipt. Staff scan the QR code, and the backend checks that the token is still valid and unused: status === 'UNCLAIMED' && validToken === true.

Check: one use only Second claim: blocked
Phase 5: Release the device and record the audit

The system invalidates the token, changes the session to COLLECTED, frees the port, and records the action in the AuditLog collection.

State: COLLECTED Audit: staff ID recorded
Claim security: A QR claim token can be used once, so a laptop or phone cannot be picked up twice.
Audit record: Each state change records the staff user ID and time in the audit ledger.
DIAGRAM 03 Background notifications
Click to view the full image
TypeScript • Async Queue Worker 
// Core transaction commits FIRST. Notification dispatches asynchronously.
export async function processSaleTransaction(payload: SalePayload) {
  const tx = await TransactionModel.create(payload);

  // Non-blocking notification dispatch
  queueMicrotask(async () => {
    try {
      await notificationService.dispatchWhatsAppReceipt(tx);
    } catch (err) {
      // Third-party network outages NEVER roll back core sales ledger
      logger.warn('[Notification] Dispatch failed, flagged for retry:', err.message);
    }
  });

  return tx;
}
Key rule: A slow WhatsApp gateway or API limit does not stop checkout or undo a completed financial transaction.
If a notification fails: The transaction succeeds first. The system retries the notification later, after checking consent.

Security and access

04 | Lessons learned

What I learned building SANFAANI

Building SANFAANI taught me how to design a system that needs reliable operations, accurate financial records, and consistent data.

Authentication vs. Authorization

A valid login JWT proves who someone is, but it does not give them every permission. Each route must check the role assigned to the user, so front-desk staff cannot view profit margins or change SKU costs.

Keep core work separate

A sale should not depend on a third-party service. If WhatsApp fails or the printer jams, MongoDB should keep the sale and a background worker should retry the notification.

Model money carefully

Unsold inventory is not revenue. Keep possible sales value separate from actual profit, and calculate profit when the sale is confirmed.

Define the data rules first

Writing the OpenAPI and Zod schemas first prevented data mismatches, runtime type errors, and a lot of manual API client work.
